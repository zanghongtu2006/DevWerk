## 1. 关联判断

两者出现在同一个项目 `prj_22d5638974ee405885b0552e4a24e91f`，都与 Loop bindings 中的项目约定有关，但直接故障不同：

| 问题 | 当前表现 | 直接缺口 |
|---|---|---|
| 六章扩至十二章 | 旧 chapter_count=6 继续阻断第7章；代理试图关闭/重建需求后陷入错误提示 | 缺少同项目范围修订及固定版本关联。 |
| 4000字硬上限 | chapter01 的4142字符仍通过 review/deliver，Task 为 done | 没有对声明的硬约束执行确定性比较。 |
| 扩写任务虚报 | 没有工具调用却说已创建、已调度 | 对话执行声明没有被真实操作结果约束。 |

共同的架构问题是：**项目约定、具体工作所用版本、可执行校验、最终报告之间没有形成完整关联。**

修订能力负责合法地改变约定；确定性验收负责执行当前工作冻结的约定；事实报告负责准确描述已经发生的结果。三者可以共享数据来源和证据关联，但不是一个通用权限判断能解决的问题。

身份错误和 Worker 退休恢复属于范围扩展的独立修复包，不与字数算法混写。修正身份错误不会自动修好字数验收；增加字数检查也不会让原项目可以扩写。

### 2.1 已有代码可以复用什么

Runtime 已能测量 `non_whitespace_characters` 并记录文件哈希；此前增加的 `acceptance_checks` 也能在完成前运行固定检查。

但目前：

- 数值进入 context 不等于执行了 `actual <= limit`；模型仍能看见4142后误判合格。
- 小说 Loop 没有声明这些固定检查，不能仅因为平台支持 acceptance_checks 就认为小说受到保护。
- `project.files.read` 成功只代表文件能读，不代表符合长度约定。
- 当前 AcceptanceCheck 只支持固定的 `project.command.run` / `project.files.read` 参数；不能假定它已经能从当前 Task 自动绑定 body_path、从 scope snapshot 自动绑定上限并验证比较关系。

因此需要把小说约定接到真正的验收执行链，而不是再增强一段提示词。

## 3. 共享基础：一个明确的工作契约版本

沿用范围修订方案的冻结关联：

```text
Project Conversation Agent
  → 用户确认的范围 revision
  → 固定 Loop 参数/方法包 + Workflow revision
  → TaskPlan / Task / Assignment
  → 对具体产物版本执行约束
  → 验收事实与状态报告
```

一份工作契约至少应能定位：

- scope/requirement revision；
- Workflow revision、Loop package digest 和 binding snapshot；
- Task 的输入及受检文件路径；
- 固定的验收规则与阈值；
- 实际读取的产物版本、哈希及检查结果。

具体案例：扩写后的新范围为12章，字数硬上限仍为4000。用户并未因扩章而要求4800。模型之前提到4800属于虚构声明，不能作为迁移输入或验收阈值。

旧工作仍绑定旧版本；新工作使用新范围。若用户以后明确修改字数上限，也必须成为新的范围修订，不能悄悄改变旧 Task 的合格标准。

## 4. 字数缺陷的独立修复包 F

### 4.1 冻结规则，由代码执行

建议复用现有完成准入与 workflow 声明结构，补充通用的产物指标校验及受限参数引用，不在 Runtime 中硬编码 chapter_number 或小说业务。

规则的概念表达如下；这不是当前已经支持的 schema：

```json
{
  "key": "body_length_limit",
  "artifact_path": {"source": "task_input", "pointer": "/body_path"},
  "metric": "non_whitespace_characters",
  "operator": "lte",
  "limit": {"source": "scope_binding", "pointer": "/chapter_max_characters"}
}
```

规则与参数来源在发布/分配时冻结。Worker 不能在完成请求里自行提交更高上限，也不能通过无关成功命令或“Reviewer 已同意”豁免失败。

v1 只需实现明确的文件指标、比较操作及已有上下文引用，不引入任意表达式解释器。可通过扩展现有验收描述与确定性 capability 来实现，schema、参数解析和执行结果必须同步发布并验证。

长度定义应固定为文档已有的“非空白字符数”：统一 UTF-8 解码和 BOM 处理，使用明确的 Unicode 空白规则；标点、数字、拉丁字母同样计入字符，不在某次检查中临时改成只统计汉字。3000 是目标，4000 才是本次明确硬上限；不能凭目标值自动增加未约定的硬下限。

### 4.2 保持 Column 职责单一

推荐在 authoring 与 review 之间加入单一确定性校验 Column：

```text
authoring → validate → review → deliver
    ↑          │         │
    └─超限退回─┘         └─正文修改意见→authoring
```

validate 不启动模型或其他 Agent，只读取当前正文、测量并比较冻结阈值。失败输出必须包含实际4142、上限4000、超出142、文件哈希和应修改的文件路径。按 workflow 声明的失败 outcome 回到 authoring；下一次分配继续原写手 context。

这是一条显式 workflow 返工边，不是在某个 Column 内运行多 Agent 循环。现有访问/恢复预算继续限制反复返工。

在 deliver 提交成功前还需要复核硬条件，防止通过 validate/review 后正文被修改。最终检查失败应按声明的失败路由回到校验/审查/返工，不应让模型反复提交 accepted 直至 CompletionProtocolStalled。

### 4.3 证据绑定同一份字节

一次确定性验收必须把计数、正文哈希、阈值、scope revision 和检查器版本关联到同一份读取的内容。

Reviewer 的叙事质量意见仍由模型提供，但 accepted 对应的正文版本要由系统记录；不要从 Markdown 中出现一个 `accepted` 字样就推导所有硬条件已满足。

deliver 只交付已经审查和校验的那个产物版本。若当前正文哈希不同，不能用旧计数/旧审查证明新正文有效；需要重新校验并审查。提交证据应引用已保存的产物快照，避免先测量一份文件、后保存另一份内容。

这样“代码测得4142，但模型说合格”也不能到达 done；模型可以继续判断故事质量，但不能改变客观比较结果。

## 6. 原项目恢复需要调整的地方

之前范围扩展方案提出“保留前六章”，这个原则继续成立；但必须补充：**保留历史不等于宣称前六章全都合格。**

本次已确认第一章超限。修复后应重新审计原有六章的确定性条件，保存审计结果，不能只看 done 状态。已发现的不合格版本与当时的错误验收记录均应保留。

对不合格章节建立独立修订工作和新产物版本，重新进行必要审查；不直接更改旧 Task 状态来掩盖错误，也不把上限升至4800以使旧4142“变合法”。本文不授权立即改写历史正文，实际修订在统一修复实施后按项目恢复流程执行。

如果第一章压缩影响事实或后续引用，应检查受影响章节的连续性；无需因此重写所有六章。新章节使用明确选定、重新验证的历史产物版本。既有 Task 依赖快照仍保留，新的修订 lineage/依赖解析需要指向对应的新验收版本，不能只替换工作区文件而保留错误的旧哈希。

扩写规划可与审计并行准备，但以历史验收为依赖的新工作，在其所依赖的必要修订未完成前不能假装已经满足依赖。

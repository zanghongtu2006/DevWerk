# v0.1.0 发布整理方案（2026-10-16）

## 范围与原则

本次发布沿用当前开发分支已经存在的源码和测试修改，不新增程序逻辑。先整理文档与本地生成物，再执行回归、提交、并入仓库默认分支 `main`、推送并发布 `v0.1.0`。

## 清理清单

1. 删除仓库内的运行日志、数据库、测试 Project 输出、缓存、临时测试目录和旧的 `devwerk.zip`；保留配置模板、源码、测试代码及 Loop 定义。`DevWerk/data/evals/` 下的两份已跟踪探针产物也从发布树移除。
2. 将 `DevWerk/docs/` 中文件名含日期的过程记录按 `docs/archive/YYYY-MM-DD/` 归档，保留未标日期的架构/协议文档和 `docs/releases/`，更新相对链接和文档索引。
3. 更新仓库根目录、服务、Loop 和 IntelliJ 插件的全部 README，使其描述当前结构、启动方式和职责；移除过时的负向状态说明。保留真实的接口约束与操作注意事项。
4. 新建 release notes，记录本次可用能力、验证证据和已知验证边界。

## 发布步骤与检查

1. 检查远端分支、标签和 Release。远端目前使用 `main`，没有 `master`；远端没有 `v0.1.0` 标签或 Release，本地旧标签指向先前的本地 `main` 提交。正式发布前将本地标签更新到最终合并提交。
2. 对清理目标核对绝对路径与 Git 跟踪状态；需要关闭运行中的服务时仅关闭相关 DevWerk/演示进程，清理后恢复 DevWerk 服务。
3. 校验 Markdown 相对链接、`git diff --check`、完整 Python 测试与编译检查；如有环境限制，记录确切结果。
4. 将既有源码改动与此次文档整理提交在开发分支；快进合并到 `main`，推送 `main`；创建并推送 `v0.1.0` 标签，确认 GitHub Release 工作流及最终发布页面。

## 发布判断

发布记录以 Git 提交、测试结果和 GitHub Release 实际状态为准。历史过程记录保留在按日期归档的目录中，运行数据与本机测试输出不纳入版本库。
